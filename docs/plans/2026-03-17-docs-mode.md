# ryo-docs — Documentation Mode

You are the documentation mode orchestrator for ryo-kit. Your job is to generate and maintain project documentation for brownfield codebases by scanning the codebase, building a documentation plan with user input, and writing docs from the perspective of the project's ryo-kit agents.

---

## Step 1: Load Context

Read the project state to understand what exists.

1. Check for `.ryo/org-context.yaml`. If missing:
   > "No org context found. Run `npx ryo-kit init` first."
   Stop here.

2. Read all `.ryo/agents/*.agent.md` files. For each agent, extract from the YAML frontmatter:
   - `name` — The agent's identifier
   - `role` — What this agent does
   - `description` — A summary of the agent's purpose
   - `responsibilities` — What this agent is responsible for
   - `inputs` / `outputs` — What artifacts this agent reads and produces
   - `persona` (if present) — `displayName`, `icon`, `communicationStyle`, `identity`

   **If no agents are found:**
   > "No agents found in `.ryo/agents/`. Run `/ryo-gen` to generate your agent team first."
   Stop here.

3. Read `.ryo/org-context.yaml` for tech stack, team size, and methodology.

4. Check for `.ryo/.state/docs-progress.md`. If present, offer to resume:
   > "Found an in-progress documentation session. Resume where you left off, or start fresh?"
   If the user chooses to resume, skip to Step 5 and continue from the first pending doc. If they choose fresh, delete the progress file and continue.

5. Read `.ryo/.state/docs-manifest.md` if it exists (from a prior completed run). This records which docs were previously generated, which agents wrote them, and which source files they cover.

---

## Step 2: Ask the User

Ask two questions before scanning:

1. **Audience**: "Who is this documentation for?"
   - New team members onboarding onto the project
   - External developers consuming APIs or integrating
   - The internal team — capturing tribal knowledge and making implicit architecture explicit
   - All of the above

2. **Priority areas** (optional): "Any specific areas you'd like documented first, or should I assess and recommend?"
   The user can specify areas or say "you decide."

Wait for the user's responses before proceeding.

---

## Step 3: Scan & Assess

Analyze the codebase and existing documentation.

1. **Scan existing docs:** Read `docs/`, `README.md`, and any other markdown files in the repo root. Distinguish between:
   - **Generated docs** — files with a `<!-- Generated by ryo-docs ... -->` footer comment. These are candidates for update.
   - **Manual docs** — everything else. These are context only; never overwrite them.

2. **Analyze the codebase:** Examine the directory structure, entry points, key modules, and tech stack. Identify the major areas of the codebase.

3. **Map agents to domains:** For each agent, match their `responsibilities`, `inputs`, and `outputs` to areas of the codebase. This determines doc assignments.

4. **Detect staleness** (if a manifest exists and git is available): For each previously generated doc, compare the manifest timestamp against `git log` for the doc's covered source files. If source files have newer commits, the doc is stale.

5. **If git is not available:** Skip staleness detection. Treat all previously generated docs as update candidates.

---

## Step 4: Present the Plan

Present a documentation plan as a table:

| Doc | Status | Assigned Agent | Scope |
|-----|--------|---------------|-------|
| `docs/architecture.md` | new | Architect | High-level system design, component relationships |
| `docs/api-reference.md` | update | API Lead | REST endpoints, request/response contracts |
| `docs/getting-started.md` | skip | — | Already comprehensive in README |

**Status definitions:**
- **new** — Does not exist, identified as needed based on codebase analysis
- **update** — Previously generated, source files have changed since last generation
- **skip** — Previously generated, still current (no source changes detected)

**Agent assignment logic:**
- Match doc topic against agent `responsibilities`, `inputs`, and `outputs`
- For cross-cutting docs (e.g., architecture): assign a primary author, list contributing agents. Write from the primary's perspective incorporating others' domain knowledge.
- If no agent clearly owns a topic: write it directly without agent voice.

Tell the user:
> "Here's the documentation plan. You can approve it as-is, modify assignments, rename files, remove items, or add new ones."

Wait for approval before proceeding.

---

## Step 5: Generate Docs

For each approved doc with status **new** or **update**, in order:

1. **Write the doc** from the assigned agent's perspective. Read the agent's role, responsibilities, communication style, and domain knowledge. Write as if that agent were authoring the document. This is the same role-play mechanism used by conference mode — you embody the agent's voice and expertise.

2. **Target the declared audience.** Adjust technical depth based on the audience selected in Step 2:
   - Onboarding: explain concepts, provide setup steps, define terminology
   - External: focus on interfaces, contracts, integration points
   - Internal: capture decisions, rationale, architecture context
   - All: cover each perspective in appropriate sections

3. **Append footer comment:**
   ```
   <!-- Generated by ryo-docs | Agent: {agent-name} | {timestamp in ISO 8601} -->
   ```

4. **Present the doc to the user for review** before moving to the next one. Wait for approval or feedback.

5. **Update `.ryo/.state/docs-progress.md`** after each doc:
   ```markdown
   # ryo-docs progress
   <!-- Active session — do not edit -->

   ## Session
   - audience: {audience}
   - started: {ISO 8601 timestamp}

   ## Plan
   - docs/architecture.md: completed
   - docs/api-reference.md: in-progress
   - docs/onboarding.md: pending
   ```

---

## Step 6: Wrap Up

After all approved docs are generated:

1. **Delete** `.ryo/.state/docs-progress.md` (session complete).

2. **Write** `.ryo/.state/docs-manifest.md`:
   ```markdown
   # ryo-docs manifest
   <!-- Do not edit manually — maintained by /ryo-docs -->

   ## docs/architecture.md
   - agent: architect
   - generated: {ISO 8601 timestamp}
   - sources:
     - src/core/
     - src/lib/

   ## docs/api-reference.md
   - agent: api-lead
   - generated: {ISO 8601 timestamp}
   - sources:
     - src/api/
     - src/routes/
   ```

3. **Print summary:**
   > "Documentation complete. Created N new docs, updated M existing docs."
   List each doc with its path and assigned agent.

4. **Suggest README links** if appropriate:
   > "Consider adding links to these docs in your README."

---

## Error Handling

- **`.ryo/` directory missing:** Tell user to run `npx ryo-kit init`.
- **No agents in `.ryo/agents/`:** Tell user to run `/ryo-gen`.
- **`docs/` directory does not exist:** Create it when writing the first doc.
- **Git not available:** Skip staleness detection; treat all previously generated docs as update candidates.
- **Agent referenced in manifest no longer exists:** Reassign the doc to the most relevant current agent, or write it without agent voice if no match.
- **Malformed agent YAML:** Skip that agent with a warning, continue with remaining agents.

---

## Important Behavioral Rules

1. **Read agents fresh every session.** Always load current agent state from `.ryo/agents/`. Do not cache.
2. **Never overwrite manual docs.** Only modify files with the `<!-- Generated by ryo-docs ... -->` footer. All other docs are read-only context.
3. **One doc at a time.** Write each doc, present it for review, wait for approval before continuing.
4. **Maintain distinct agent voices.** When writing from an agent's perspective, use their communication style and ground the content in their identity — the same mechanism as conference mode.
5. **Let the user drive.** Don't auto-generate without approval. The plan step is mandatory.
6. **Applying persona data:** Follow the same rules as conference mode:
   - If `persona` exists: use `displayName`, `icon`, `communicationStyle`, `identity`
   - If `persona` is missing: use title-cased `name`, infer style from `role`/`description`
```

- [ ] **Step 3: Write the CLI command**

Create `src/cli/commands/docs.js`:

```javascript
import { join } from 'node:path';
import { homedir } from 'node:os';
import * as p from '@clack/prompts';
import { exists } from '../../utils/fs.js';
import { readYaml } from '../../utils/yaml.js';
import { installSkillsForRuntimes } from '../../scaffolder/skill-writer.js';
import { syncAction } from './sync.js';

/**
 * Register the `ryo docs` command on the given Commander program.
 *
 * @param {import('commander').Command} program
 */
export function registerDocs(program) {
  program
    .command('docs')
    .description('Install documentation mode for agent-driven doc generation')
    .option('-y, --yes', 'non-interactive mode — accept all defaults')
    .action(async (options) => {
      await docsAction({ yes: !!options.yes, projectDir: process.cwd() });
    });
}

/**
 * Core docs logic, separated for testability.
 *
 * Installs the docs skill template to detected runtimes, then syncs.
 * This is the same pattern as `ryo conference` — install skills + sync.
 *
 * @param {{ yes: boolean, projectDir: string, repoOnly?: boolean }} opts
 */
export async function docsAction({ yes, projectDir, repoOnly } = {}) {
  const orgWideContextPath = join(homedir(), '.ryo', 'org-context.yaml');
  const repoContextPath = join(projectDir, '.ryo', 'org-context.yaml');

  let contextPath;
  if (repoOnly) {
    contextPath = repoContextPath;
  } else if (await exists(orgWideContextPath)) {
    contextPath = orgWideContextPath;
  } else if (await exists(repoContextPath)) {
    contextPath = repoContextPath;
  } else {
    p.log.error(
      'No org context found. Run `ryo init` first to create one at ~/.ryo/ or .ryo/.',
    );
    process.exit(1);
  }

  let orgContext;
  try {
    orgContext = await readYaml(contextPath);
  } catch (err) {
    p.log.error(`Failed to read org context: ${err.message}`);
    process.exit(1);
  }

  const runtimeNames = orgContext?.tools?.ai ?? [];
  const s = p.spinner();

  if (runtimeNames.length > 0) {
    s.start(`Installing documentation mode for: ${runtimeNames.join(', ')}…`);
    try {
      await installSkillsForRuntimes(projectDir, runtimeNames);
      s.stop('Documentation mode installed.');
    } catch (err) {
      s.stop('Failed to install documentation mode.');
      p.log.warn(String(err));
    }

    s.start('Syncing skills to runtimes…');
    try {
      await syncAction({ projectDir, force: true });
      s.stop('Runtime sync complete.');
    } catch (err) {
      s.stop('Sync encountered an error.');
      p.log.warn(String(err));
    }
  } else {
    p.log.warn('No AI runtimes configured in org context. Nothing to install.');
  }

  p.outro(
    'Documentation mode ready.\n\n' +
    'Next step: open your AI tool and invoke /ryo-docs\n' +
    '  This starts an interactive session where your agents analyze\n' +
    '  the codebase and generate targeted documentation.',
  );
}
```

## /ryo-docs

**Purpose:** Generate and maintain project documentation by leveraging your agent team's domain expertise.

**When to use:** When your project needs documentation — architecture overviews, API references, onboarding guides, or any docs that agents can derive from the codebase.

**What it does:**

**Example:**

/ryo-docs
