# Documentation Mode Design Spec

## Overview

Documentation mode is an orchestrator-driven skill that generates and maintains project documentation for brownfield codebases. It scans the codebase and existing docs, builds a documentation plan with user input, then writes docs from the perspective of the project's ryo-kit agents based on their domains of responsibility. It supports creating new docs, updating stale ones, and skipping what's already covered.

## Goals

- Generate useful project documentation (architecture, API, onboarding, etc.) by leveraging agent expertise
- Support multiple audiences: onboarding, external developers, internal team, or all
- Be aware of existing documentation — identify gaps, detect staleness, avoid duplication
- Produce living documentation that can be refreshed as the codebase evolves
- Output plain markdown in `docs/` that's useful to anyone, regardless of ryo-kit

## Non-Goals

- Replacing existing documentation tooling (JSDoc, Swagger, etc.)
- Generating code comments or inline documentation
- Running without prior `ryo-kit init` and `/ryo-gen` — agents are required
- Hardcoding a fixed set of doc types — agents determine what's needed

---

## 1. Prerequisites

The skill requires:
- `.ryo/org-context.yaml` exists (from `ryo-kit init`)
- `.ryo/agents/` contains at least one agent (from `/ryo-gen`)

Both prerequisites are validated **at skill invocation time** (Step 1 of the skill template), not at CLI install time. The CLI command is "dumb" — it installs the skill template and syncs to runtimes, nothing more. This matches the conference mode pattern where the CLI does not validate agent existence.

If either prerequisite is missing when the user invokes `/ryo-docs`, the skill exits with a message directing the user to run the appropriate command.

---

## 2. CLI Command

New file: `src/cli/commands/docs.js`

### Usage

```
ryo docs
```

### Behavior

The CLI command installs the skill template — it does **not** generate documentation. The pattern matches `ryo conference`: CLI scaffolds, user invokes the slash command in their AI tool.

1. Resolve org context (same pattern as `ryo gen`)
2. Call `installSkillsForRuntimes(projectDir, runtimeNames)` to install all core skills (including `ryo-docs`) and sync to configured runtimes — this is the same mechanism used by conference mode, not a selective single-skill install
3. Print usage instructions:
   ```
   ◇ Documentation mode installed. Use /ryo-docs in your AI tool to start a session.
   ```

### Registration

Added to `src/cli/index.js` via `registerDocs(program)`.

### Flags

- `-y, --yes` — Skip confirmation (consistent with other commands)

Note: `projectDir` and `repoOnly` are available as internal action function parameters for testing (matching the conference mode pattern) but are not exposed as user-facing CLI flags.

## 3. Skill Template

New file: `templates/core-skills/ryo-docs.skill.md`

As a core skill, `ryo-docs` is installed alongside all other core skills whenever any install/sync runs. The `ryo docs` CLI command is a convenience entry point, but the skill will also be present after `ryo gen` or `ryo evolve`.

### Skill Frontmatter

```yaml
---
name: ryo-docs
description: >
  Documentation generation and maintenance skill. Scans the codebase and existing
  docs, builds a documentation plan with user input, then writes documentation from
  the perspective of project agents based on their domains of responsibility.
trigger: /ryo-docs
---
```

### Step 1: Load Context

- Check for `.ryo/org-context.yaml` — if missing, tell user to run `ryo-kit init` and stop
- Check for `.ryo/agents/*.agent.md` — if none found, tell user to run `/ryo-gen` and stop
- Read `.ryo/org-context.yaml` for tech stack, team size, methodology
- Read all `.ryo/agents/*.agent.md` to build the agent roster with roles, responsibilities, and persona data
- Check for `.ryo/.state/docs-progress.md` — if present, offer to resume the in-progress session (see Section 7 for resume logic)
- Read `.ryo/.state/docs-manifest.md` if it exists (from prior completed runs)

### Step 2: Ask the User

- **Audience**: Who is this documentation for? (new team members onboarding, external developers consuming APIs, the internal team capturing knowledge, or all of the above)
- **Priority areas** (optional): Any specific areas of concern? The user can say "you decide" and the agents will determine what's needed.

### Step 3: Scan & Assess

- Scan `docs/`, `README.md`, and any other markdown files in the repo
- Distinguish between generated docs (those with a `<!-- Generated by ryo-docs ... -->` footer) and manually-maintained docs — only generated docs are candidates for "update" status; manually-maintained docs are always shown as context, never overwritten
- Analyze the codebase structure — directories, entry points, key modules, tech stack
- For each agent, map their responsibilities to areas of the codebase
- Cross-reference existing docs against codebase coverage
- Identify: what's well-documented, what's missing, what needs updating (using git history comparison against the docs manifest if available; if git is not available, skip staleness detection and treat all generated docs as candidates for update)

### Step 4: Present the Plan

Output a documentation plan as a table:

| Doc | Status | Assigned Agent | Scope |
|-----|--------|---------------|-------|
| `docs/architecture.md` | new | Architect | High-level system design, component relationships |
| `docs/api-reference.md` | update | API Lead | REST endpoints, request/response contracts |
| `docs/getting-started.md` | skip | — | Already comprehensive in README |

Status definitions:
- **new**: Does not exist, agents identified it as needed
- **update**: Previously generated and source files have changed since last generation
- **skip**: Previously generated and still current (no source changes detected)

The user can approve, modify assignments, rename files, remove items, or add new ones before generation begins.

### Step 5: Generate Docs

For each approved doc (new or update):

1. The orchestrator writes the doc from the assigned agent's perspective — reading the agent's role, responsibilities, communication style, and domain knowledge to shape the content. This is the same "role-play" mechanism used by conference mode: the skill reads agent definitions and writes as if that agent were authoring the doc. There is no separate agent process; the orchestrator embodies each agent in turn.
2. The doc is written targeting the declared audience, with appropriate technical depth
3. A footer comment is appended: `<!-- Generated by ryo-docs | Agent: {agent-name} | {timestamp} -->`
4. The user reviews the doc before the skill moves to the next one
5. After each doc is written, update `.ryo/.state/docs-progress.md` with current state

### Step 6: Wrap Up

- Delete `.ryo/.state/docs-progress.md` (session complete)
- Print a summary of what was created and updated
- Persist `.ryo/.state/docs-manifest.md` (see Section 7 for format)
- Suggest adding doc links to README if appropriate

### Error Handling

- **Missing `.ryo/` directory**: Tell user to run `ryo-kit init`
- **No agents in `.ryo/agents/`**: Tell user to run `/ryo-gen`
- **`docs/` directory does not exist**: Create it when writing the first doc
- **Git not available**: Skip staleness detection; treat all previously generated docs as update candidates
- **Agent referenced in manifest no longer exists**: Reassign the doc to the most relevant current agent, or to the orchestrator if no match
- **Malformed agent YAML**: Skip that agent with a warning, continue with remaining agents

---

## 4. Agent Assignment Logic

The orchestrator assigns docs to agents based on domain matching:

- Each agent's `responsibilities`, `inputs`, and `outputs` fields are compared against the documentation topic
- Example: an agent responsible for "API design" is assigned the API reference doc; a "DevOps" agent gets deployment/infrastructure docs
- **Cross-cutting docs** (e.g., architecture overview): the orchestrator assigns a primary author and lists contributing agents. The doc is written from the primary's perspective but incorporates knowledge from contributing agents' domains.
- **Unowned topics**: if no agent clearly owns a topic, the orchestrator writes it directly without agent voice
- Assignments are shown in the plan (Step 4) and the user can reassign before generation

---

## 5. Staleness Detection & Refresh

When `/ryo-docs` is run on a project with existing generated docs:

1. Read `.ryo/.state/docs-manifest.md` to find previously generated docs and their covered source paths
2. For each doc, compare the manifest timestamp against `git log` for the covered files
3. If covered files have commits newer than the manifest timestamp, mark the doc as **update**
4. If no changes detected, mark as **skip**
5. New areas of the codebase not covered by any existing doc are proposed as **new**

The user can override any status in the plan step (force regenerate a "skip", or skip an "update").

---

## 6. Output Format

- All docs are written to `docs/` at the project root
- Generated docs coexist with manually-maintained docs — the skill identifies generated docs by their `<!-- Generated by ryo-docs ... -->` footer and never modifies files without this marker
- Each doc is a standalone markdown file
- Filenames are determined by the orchestrator based on content and shown in the plan for user approval
- Each doc includes a footer comment for manifest correlation: `<!-- Generated by ryo-docs | Agent: {agent-name} | {timestamp} -->`
- No ryo-kit-specific formatting — docs are plain markdown usable by anyone
- No auto-generated index file, but the wrap-up suggests linking from README

## 7. State Management

### docs-manifest.md

Persisted after each completed run. Format:

```markdown
# ryo-docs manifest
<!-- Do not edit manually — maintained by /ryo-docs -->

## docs/architecture.md
- agent: architect
- generated: 2026-03-17T14:30:00Z
- sources:
  - src/core/
  - src/lib/
  - src/cli/index.js

## docs/api-reference.md
- agent: api-lead
- generated: 2026-03-17T14:35:00Z
- sources:
  - src/api/
  - src/routes/
```

Each section corresponds to one generated doc, with the agent that wrote it, the generation timestamp, and the source paths it covers (used for staleness detection against `git log`).

### docs-progress.md

Written during an active session to enable resume after interruption. Format:

```markdown
# ryo-docs progress
<!-- Active session — do not edit -->

## Session
- audience: all
- started: 2026-03-17T14:25:00Z

## Plan
- docs/architecture.md: completed
- docs/api-reference.md: in-progress
- docs/onboarding.md: pending
- docs/deployment.md: pending
```

On Step 1, if this file exists, the skill offers to resume from where it left off (skipping completed docs, continuing from the in-progress or next pending doc). If the user declines, the file is deleted and a fresh session begins.
